# aiagents

> **Status: alpha.** Interfaces, file layout and placeholders may change between minor versions. Read the Safety notes before giving agents access to anything that matters.

> **New here? Read [HOWTO.md](HOWTO.md)** — plain-language guide: how to start with the `lead` agent, approval gates, a worked first day, and a cheat sheet.

A reusable, project-agnostic kit for running software projects with AI agents (OpenCode and VS Code GitHub Copilot) and humans in clear roles. Extracted from real multi-repo projects. **Docs, config and prompts only**: no application code, no infrastructure specifics, no secrets.

What a project gets:
- **Agents** (one source per agent, generated for OpenCode and VS Code): `lead` (single entry point, orchestrates everything with owner approval gates), `explorer` (read-only discovery of existing code), `architect`, `developer`, `infra-developer`, `test-engineer`, `security-reviewer`, `domain-reviewer`, `quick-tasks`, `ticket-tracker` (optional: updates ticket and wiki after a verified merge).
- **Skills** (`.agents/skills/`): `project-intake`, `document-ingest`, `requirements-register`, `backlog-planning`, `dispatch-tasks`, `status-report`, `project-state`, `codebase-discovery`, `task-intake`, `cross-repo-feature`, `project-setup`, `release-checklist`, `tdd`, `code-review`, `diagnosing-bugs`, `grilling`, `domain-modeling`, `codebase-design`, `pr`, `writing-for-agents` + repo-type and pack skills.
- **Process docs**: `AGENTS.md` with "Definition of done: documentation", ticket standard, issue forms, PR template, release and security checklists, service map, ADR template, glossary.
- **Prompts**: ready-to-paste prompts, also as VS Code prompt files (`.github/prompts/`).

## Structure

```
core/            agents (incl. lead, explorer), commands/ (/setup source), skills, scripts/sync-agents.py, github/ templates,
                 docs-templates/ (+ project/: brief, requirements register, state, status report,
                 decision brief, dossier, worked examples → installed to docs/agents/templates/), placeholders.yaml
repo-types/      backend-go, frontend-nextjs, serverless-sam, docs-hub (AGENTS section, agent overrides, skills,
                 CONTRIBUTING/README skeletons, PR checklist additions, type.yaml)
packs/           optional: multi-tenant-saas, payroll-gr, postgres-infra, aws-serverless-cost, auth-sessions-mfa
prompts/         00-start-here + 00-11 prompts (Markdown) + vscode/*.prompt.md (generated by scripts/build-prompts.py)
scripts/         apply-kit.py, check-kit.py, build-prompts.py, kitlib.py, test_*.py (python3 stdlib only)
examples/        bookit/ — small invented toy example (fictional salon booking app) showing the project docs the kit produces
```

Override order: core → repo type → packs (a later file with the same target path wins; the report shows it). Example: `repo-types/backend-go/agents/developer.md` replaces the generic developer; `packs/payroll-gr/agents/domain-reviewer.md` turns the domain reviewer into a payroll reviewer.

## Quick start (with /setup)

```sh
git clone <this repo> ~/src/aiagents                              # once
cd ~/src/my-project                                                # your already-cloned project
python3 ~/src/aiagents/scripts/apply-kit.py --target . --bootstrap # adds only the /setup command
```

Open the project in OpenCode or VS Code (Copilot agent mode) and type `/setup`. It detects the stack, the project name and the AI tool, then asks a few questions **one at a time** (each with a recommended answer; `skip` is always fine):
1. confirm the detected stack; 2. project name and owner;
3. connections, tool-neutral: which code host (GitHub, GitLab, other, none), which ticket tracker (Jira, Linear, GitHub Issues, other, none), which wiki, and **how** agents reach each one (`mcp`, `cli`, `api` or `manual`). The kit records the answers in placeholders and shows the generic login (in your browser or your own terminal) and read-only check. It never asks for tokens, passwords, servers or databases. Skips have fallbacks: no code host → commit locally and report; no tracker → `docs/work-log.md` with `LOCAL-<n>` keys; no wiki → no mirroring.
4. a yes/no per relevant pack (from the detected stack and keywords) and for the extra role agents.

It then shows the `apply-kit.py --profile lean ...` command, runs a dry run, installs after your "yes" and writes `.aiagents/access.md` (what is connected, how, what was skipped). The `lead` reads that file at session start and passes it to agents as the `Access:` line. Later: `/setup add <pack or agent>`, `/setup access`.

The **lean profile** installs `lead`, `explorer`, nine core skills (`task-intake`, `dispatch-tasks`, `tdd`, `diagnosing-bugs`, `code-review`, `grilling`, `domain-modeling`, `codebase-design`, `pr`), `AGENTS.md`, the interaction standard, access-and-conflicts, the work-log template and the `/setup` command, plus the packs and agents you accepted. Some lean files still point to docs only the full profile installs (for example the ticket standard); add them with `--profile full --update` when you need them.

Not tested yet: the interview has only been checked as generated files and through the script; running it end to end inside OpenCode and VS Code is still open (alpha).

### Manual install (full profile, as before)

```sh
python3 ~/src/aiagents/scripts/apply-kit.py --type backend-go --target ./my-api \
  --set PROJECT_NAME=Acme --set ORG=acme --set DOCS_REPO=acme-docs --pack multi-tenant-saas --dry-run
python3 ~/src/aiagents/scripts/apply-kit.py ...same arguments without --dry-run...
```

Then open the target in OpenCode or VS Code and talk to `@lead` with `prompts/00-start-here.md`. Or, manually, in the target: review the report, fill `docs/architecture/service-map.md` / `GLOSSARY.md` (docs hub), create labels from `docs/agents/ticket-standard.md`, commit on a branch, open a PR. Easiest path: paste `prompts/00-new-project-bootstrap.md` or `prompts/01-existing-project-onboarding.md` into your agent; it runs the `project-setup` skill and asks before writing anything.

### apply-kit.py

```
python3 scripts/apply-kit.py --type backend-go|frontend-nextjs|serverless-sam|docs-hub --target <dir>
    --set KEY=VALUE ... [--pack <pack> ...] [--standalone] [--profile lean|full] [--agent <name> ...] [--dry-run]
python3 scripts/apply-kit.py --target <dir> --update [--set KEY=VALUE ...] [--pack <new pack>] [--agent <name>] [--dry-run]
python3 scripts/apply-kit.py --target <dir> --bootstrap [--dry-run]   # only the /setup command files
python3 scripts/apply-kit.py --target <dir> --detect                 # read-only guesses as JSON
```

- `--profile full` is the default (unchanged behaviour); `--profile lean` is what `/setup` uses. `--agent` adds agents to a lean install. Profile, packs and agents are stored in the manifest; `--update` keeps them and adds new `--pack`/`--agent` choices (old manifests without a profile count as full).
- `--bootstrap` writes `.opencode/commands/setup.md`, `.github/prompts/setup.prompt.md` (both generated from `core/commands/setup.md`) and the git-ignored `.aiagents/kit.local` (the kit path). A later install adopts identical existing files instead of skipping them.

- Never overwrites existing files; prints created / skipped / conflict lists.
- Errors on missing required placeholders (`PROJECT_NAME`, `ORG`, `DOCS_REPO`; `DOCS_REPO` defaults to the repo itself for `docs-hub` and `--standalone`) and on any unresolved placeholder.
- `--standalone`: single-repo project; also installs service map, ADR template, glossary and onboarding.
- Writes `.aiagents-manifest.json` (kit version, type, packs, `--set` values, file hashes) and runs `scripts/sync-agents.py` and `--check` in the target.
- `--update`: re-renders with stored values; updates files whose content still matches the manifest hash, reports locally modified files as conflicts (exit 1) and leaves them alone. Never put secrets in `--set` values.

Placeholders: global ones in `core/placeholders.yaml`, per type in `repo-types/<type>/type.yaml`, per pack in `packs/<pack>/pack.yaml` (each with defaults and descriptions). Precedence: core defaults < type < packs < stored manifest values < `--set`.

## Interaction standard

Agents ask the owner **one question at a time** with a recommended answer and options (`core/docs-templates/interaction-standard.md.tmpl`, installed to `docs/agents/interaction-standard.md`). Every agent source carries the short form in its Rules; `check-kit.py` enforces it.

## Agent source format and roles

`agents/<name>.md` with flat frontmatter (`name`, `description`, `role`, optional `model`, `mode`, `extra_permissions`); `scripts/sync-agents.py` generates the OpenCode and VS Code files.

| Role | OpenCode | VS Code |
|---|---|---|
| `implementer` | edit allowed | all enabled tools |
| `reviewer` | no edits; read-only git/gh | `read`, `search` |
| `planner` | as reviewer | `read`, `search`, `web` |
| `inspector` | no edits; every shell command asks | `read`, `search`, `execute` |
| `docs` | edits only `*.md` | `read`, `search`, `edit`, `todo` |
| `orchestrator` | `mode: primary`; edits only `*.md` and `docs/*`; read-only git/gh incl. `gh issue list`, `gh pr list/checks`; `subagent` `*` allowed | `read`, `search`, `edit`, `web`, `todo`, `agent` + `agents: ['*']` (Local harness subagents; `edit` cannot be path-limited in VS Code) |

All roles: OpenCode adds `question` `*` allow (structured owner questions); VS Code roles with a `tools` list also get `vscode/askQuestions` (implementers use all enabled tools).

## Updating the kit and versioning

- `VERSION` holds the kit version (semver); every change gets a `CHANGELOG.md` entry. Minor: new agents/skills/packs/prompts; patch: wording; major: changed placeholders or target paths.
- Before committing: `python3 scripts/build-prompts.py` (if prompts changed) and `python3 scripts/check-kit.py` (skills/agents valid, placeholders declared, prompts in sync, forbidden-string scan).
- Projects pull improvements with `apply-kit.py --target <repo> --update`, review the diff and conflicts, open a PR.

## How improvements flow back

1. A project improves an agent, skill or checklist (in its repo, via a normal PR).
2. If the improvement is not project-specific, open a PR here that ports it: remove project facts, use placeholders, put it in `core/`, a repo type or a pack.
3. `check-kit.py`, CHANGELOG entry, VERSION bump; then projects `--update`.
4. Project-only facts stay in the project (or become a new pack).

## Lessons learned (embedded in agents, checklists and prompts)

1. **Verify `main` contains the reviewed commits before releasing.** A squash merge taken from an early commit can drop later fixes. Compare the PR head tree with the merge result.
2. **Never build or deploy unless lint/test/security pass in the same run** (`needs:` on the check jobs).
3. **Agents never read or print secret values.** Check secret *names* only; a tool that shows configuration can leak credentials into chat logs.
4. **Deploy secrets come from CI environment secrets**, written by the deploy job to root-only files; never hand-edited on servers.
5. **Branch protection features vary by plan** (e.g. required reviewers may be unavailable): document accepted risks and their preconditions (e.g. restrict environments before adding collaborators).
6. **Reviewers are read-only**; implementers hand off to `test-engineer` → `security-reviewer` → human merge.
7. **Review twice** when a PR touches auth, sessions or crypto: initial review and after fixes.
8. **Docs are part of done** — every agent report lists the docs it updated.
9. **Contract first** for APIs; consumers build only against the merged contract.
10. **Mark legal/domain claims "to be validated by an expert"**; never invent statutory figures or external API contracts.
11. **Parallel agents conflict.** List files per agent first, serialize overlaps, state the merge order, re-check open PRs after every merge, never merge before the final report, and verify `main` by content (not SHA).
12. **Missing access is normal.** Check once with a cheap read-only call, say it once, pass an `Access:` line to agents, fall back to a plain work-log (`LOCAL-<n>`), never invent keys or claim updates that did not happen.

## Safety notes

- **Agents act with the permissions you give them.** Review each agent's permissions and tool list (generated by `sync-agents.py` into `.opencode/agents/` and `.github/agents/`) before use, and tighten them for your project.
- **Never give agents production credentials** or access to production data; keep owner-only steps (servers, releases, secrets) with a human.
- **AI output must be reviewed by a human** before it is merged, released or relied on. Domain and legal statements in packs are not professional advice.
- **No warranty.** The kit is provided "as is" under the MIT License.
- Before committing to the kit, `check-kit.py` scans for secrets and identifiers. Put your own domains and organisation names in an untracked `.kit-forbidden.txt` (one regex per line; ignored by git) so they are caught too; see [CONTRIBUTING.md](CONTRIBUTING.md).
